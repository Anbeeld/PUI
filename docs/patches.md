# PUI patches

PUI owns the configuration and targeted patches that make its upstream components work as one reproducible application without a Pi fork. The [component reference](components.md) lists upstream packages and repository structure.

## Managed files and fields

PUI makes timestamped backups before inspecting or changing existing configuration JSON. It structurally merges the owned fields below except for the create-only `~/.config/pui/reasoning-summaries.json` and `~/.config/pui/session-titles.json` files and the optional `~/.config/pui/model-policy.json`, whose lifecycles are documented separately. The native recovery path also backs up `~/.pi/agent/npm/package.json` before asking npm to record its exact `node-pty` script approval:

- `~/.pi/agent/settings.json`: `defaultTools`, managed package entries, and explicitly retired package entries
- `~/.pi/web-search.json`: `searchRouting`, `fetchRouting`, and `workflow`
- `~/.config/mcp/mcp.json`: `mcpServers.playwright.command`, `args`, `lifecycle`, the six-tool `directTools` policy, and `settings.mcpFooterStatus`
- `~/.pi/agent/pi-goal.json`: `continuationLimits.automaticTurns` and `continuationLimits.noProgressTurns`
- `~/.config/rpiv-ask-user-question/config.json`: exact `guidance.description`, `guidance.promptSnippet`, and `guidance.promptGuidelines` values; an existing absolute `$XDG_CONFIG_HOME/rpiv-ask-user-question/config.json` takes precedence
- `~/.pi/agent/npm/package.json`: only the exact `node-pty` lifecycle approval when a native rebuild is required
- `~/.pi/agent/npm/node_modules/@99percentpeople/pi-background-tasks/index.min.js`: exact PUI-owned tool metadata plus per-extension-instance runtime-state isolation; the upstream bundle is retained as `index.min.js.pui-original` and ownership hashes as `index.min.js.pui-manifest.json`
- `~/.pi/agent/npm/node_modules/@gotgenes/pi-subagents/` sources listed by `stack.json.subagentsPromptPatch.files`: exact PUI-owned taxonomy, routing guidance, child-prompt inheritance filtering, capability allowlists, unknown-type handling, per-instance running/queued limits, result-integrity, mapped-model, parent-reasoning, and completion-delivery policy; each upstream file is retained as `<file>.pui-original` and ownership hashes as `.pui-subagents-prompt-manifest.json`
- `~/.config/pui/subagents.json`: user-editable fuzzy model mappings plus `_pui.defaultMappings` reconciliation metadata; updates preserve user changes and deletions while adding newly shipped defaults
- `~/.config/pui/reasoning-summaries.json`: create-only user configuration with `schemaVersion: 1` and a `modelModes` object; a missing file receives the three `gpt-5.6-*` `detailed` defaults, while any existing valid file remains byte-for-byte unchanged
- `~/.config/pui/session-titles.json`: create-only user configuration with `schemaVersion: 1` and an ordered `models` array of exact `provider/model-id` or fuzzy selectors; new files start with an empty list and use the active session model
- `~/.config/pui/model-policy.json`: optional user configuration with provider-grouped, exact-model capability rules; version 1 supports one tool `allow` or `deny` list per configured model
- Pi Web's resolved unbundled `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js` and `@earendil-works/pi-agent-core/dist/agent-loop.js`: temporary exact Pi #8782 runtime backport; originals are retained beside the targets as `*.pui-8782-original` and ownership hashes as `.pui-pi-8782-backport.json`
- Exact Pi Web and standalone Pi compiled display/provider seams selected by `pui-reasoning-summary-patch.js` under the version and ownership policy in `reasoningSummaryPatch`: Responses reasoning-summary compatibility for any model using the managed Responses adapters, canonical Pi Web goal-command display, compaction-style typography for visible `Goal complete` bodies, and collapsed-by-default Pi Web subagent notifications; originals use `.pui-reasoning-original` and each runtime root records hashes in `.pui-reasoning-summary.json`
- `~/.pi/agent/extensions/pui-update/`: installed PUI identity and detached transaction worker
- `~/.pi/agent/extensions/pui-skill-loader/`: exact PUI-owned `load_skill` extension source, package metadata, and hash manifest
- `~/.pi/agent/extensions/pui-reasoning-summary/`: exact PUI-owned Responses request-policy extension source, package metadata, and hash manifest
- `~/.pi/agent/extensions/pui-session-title/`: exact PUI-owned automatic-title extension source, package metadata, and hash manifest
- `~/.pi/agent/extensions/pui-session-communication/`: exact PUI-owned Pi Web session-tool extension source, package metadata, and hash manifest
- `~/.pi/agent/extensions/pui-model-catalog/`: exact PUI-owned `model_list` extension source, package metadata, and hash manifest
- `~/.pi/agent/extensions/pui-model-policy/`: exact PUI-owned model capability-policy source, package metadata, and hash manifest

The reasoning-summary extension handles request generation separately from `pui-reasoning-summary-patch.js`, which remains responsible for safe parsing and display. On `before_provider_request`, it uses `ctx.model.api`, `ctx.model.provider`, and `ctx.model.id`; it never trusts the payload's model field. It is restricted to `openai-responses`, `azure-openai-responses`, and `openai-codex-responses`. An exact `provider/model-id` configuration key wins over an exact bare `model-id`. Modes `auto`, `concise`, and `detailed` set `reasoning.summary`; `none` removes it. A missing or invalid configuration, unsupported API, unknown model, absent reasoning object, or `effort: "none"` leaves the payload unchanged.

The default file is:

```json
{
  "schemaVersion": 1,
  "modelModes": {
    "gpt-5.6-sol": "detailed",
    "gpt-5.6-terra": "detailed",
    "gpt-5.6-luna": "detailed"
  }
}
```

Install and update create that file only when missing. Existing valid content—including changed values, removed entries, additional valid entries, formatting, and unknown top-level fields—is preserved byte-for-byte. Existing invalid content is backed up, is not overwritten, and stops the lifecycle operation. Doctor validates the schema. Uninstall preserves the configuration. The installed extension itself uses exact manifest hashes: install/update replace only a verified PUI-owned target, doctor verifies it, uninstall preserves drift, and update rollback restores the complete previous directory.

The model-catalog extension exposes `model_list` in standalone Pi and Pi Web and installs the versioned `pui.model-resolver.v1` in-process service used by PUI's model catalog, session-title extension, Pi Web session broker, and subagent integration. The resolver checks case-insensitive exact `provider/model-id` references first, accepts a bare ID only when it is unique across providers, ranks normalized fuzzy matches deterministically, prefers stable aliases over dated variants and the newest dated variant when no alias exists, and rejects otherwise tied winners when a consumer needs one model. Colons and additional slashes inside a model ID remain part of its exact identity. Reasoning-effort metadata follows Pi 0.84.3: non-reasoning models expose only `off`, explicit `null` mappings remove levels, and `xhigh` or `max` require explicit support.

`model_list` reads `ctx.modelRegistry.getAvailable()`, so results include only models available through the provider authentication configured for the running Pi instance. Results are grouped by provider. Each model includes its exact `provider/model-id`, display name, API, context window, maximum output tokens, text/image and reasoning capabilities, USD-per-million-token input/output/cache rates, optional pricing tiers, and supported reasoning efforts. An omitted `query` returns the complete available set. A query also returns a flat `matches` array that preserves global resolver rank and includes each candidate's exact ID, rank, score, and match kind rather than silently choosing an ambiguous winner. The tool does not refresh or alter Pi's model registry.

The separate model-policy extension provides a generic per-model capability boundary. Version 1 implements tool policy. Provider and model IDs match exactly and are not fuzzy aliases. Each model entry defines exactly one `tools.allow` or `tools.deny` array. An allowlist retains only listed tools that were already active; a denylist removes listed tools. On session start, model change, each new outer turn, and tool-result delivery, the extension updates Pi's active tools, which removes prohibited tool definitions, prompt snippets, and tool-owned guidelines from subsequent model requests. It restores only tools that the policy itself removed when the active model becomes less restrictive, preserving unrelated disabled tools. A `tool_call` guard independently blocks prohibited or stale calls. Text from AGENTS.md or other unrelated prompt sources is not rewritten.

```json
{
  "schemaVersion": 1,
  "providers": {
    "openai-codex": {
      "models": [
        {
          "id": "gpt-x",
          "tools": {
            "deny": ["subagent", "session_start"]
          }
        }
      ]
    }
  }
}
```

A missing policy file is unrestricted. Install and update do not create it or treat its absence as a failure; they preserve every valid existing byte and stop without overwrite after backing up invalid content. At runtime, malformed existing policy disables all active tools and blocks tool execution until the file is corrected; doctor reports it as invalid. Uninstall preserves the policy file. The extension directory uses the same exact-file manifest, drift preservation, snapshot, rollback-guard, and ownership-safe removal contract as the other PUI-owned extensions.

The session-title extension listens at Pi's `before_agent_start` seam. For a new unnamed session with no prior substantive text, it marks the attempt synchronously and detaches generation so the main agent starts without waiting. It uses the expanded first prompt's text only; image-only turns do not consume the one attempt. Fenced code or logs are removed when surrounding prose is available, whitespace is collapsed, and the remaining input is limited to 600 Unicode code points using both the beginning and end. The request is one user message whose input is embedded as a JSON string, with no system prompt, tools, session history, or session cache identifier. It directly prohibits reasoning and explanation and requires the result between exact `<pui-session-title>` and `</pui-session-title>` markers. It requests `reasoningEffort: "none"` when supported and otherwise selects the first supported level in `minimal`, `low`, `medium`, `high`, `xhigh`, `max` order from the model's reasoning metadata. It uses a 1,024-token output ceiling, a ten-second provider timeout, two provider retries, and a 30-second overall deadline that also aborts with the run or session shutdown.

Configured model selectors are resolved in order through the shared PUI model resolver. Unavailable selectors are skipped, duplicate resolved provider/model pairs are removed, at most four configured models are tried, and the active session model is appended as the final fallback. A response is usable only when it contains a non-nested exact title-marker pair; when multiple valid pairs exist, the final pair wins. Text outside the marker is ignored, so a provider that exposes deliberation as ordinary text cannot turn that prose into a title. The marked value is stripped of terminal control sequences, title tags or labels, wrapping quotes or backticks, whitespace, and ending punctuation. A marked value containing nested markup or line breaks, whitespace-separated output over 12 words, output over 80 Unicode code points, or output with nothing alphanumeric is rejected so malformed output advances to the next candidate. Empty, aborted, deferred, or failed responses advance to the next candidate. Complete failure is silent. Immediately before persistence, the extension rechecks the in-memory session name, its own session-info events, and the persisted session file so an explicit or concurrent manual name—including a Pi Web rename written through a separate session manager—wins.

The default file is:

```json
{
  "schemaVersion": 1,
  "models": []
}
```

For example, `"models": ["openai-codex/gpt-5.6-luna", "haiku"]` tries the exact available Luna identity first, then the best available fuzzy Haiku match, then the active session model. Install and update create the file only when missing; valid existing bytes and unknown top-level fields are preserved. Invalid content is backed up without overwrite and stops the lifecycle operation. Doctor validates both configuration and extension identity, uninstall preserves the configuration and any drifted extension directory, and update transactions restore or remove the extension according to its prior state.

The skill-loader extension keeps Pi's discovered skill names and descriptions in the system prompt as routing metadata. When `load_skill({ name })` is called, it resolves only an exact discovered name, rejects files over 50 KB or 2,000 lines without returning partial content, and returns the skill body with its directory plus a sorted list of direct regular `references/*.md` files. `load_skill({ name, reference })` accepts one or more listed filenames with or without `.md` as a single value or a list, rejects paths, traversal, non-Markdown files, symlinks, and unavailable references, and validates a whole list before loading anything. If the parent skill's tool result is absent from active context, the same result includes the skill body before the requested reference bodies. A batched load returns one structured result: the optional parent skill, a summary naming newly loaded and already loaded references, then each loaded reference body under its own heading, with the combined output bounded by the same limits. Context-derived ownership keeps duplicate loads idempotent while permitting the skill or a reference to reload after compaction or tree navigation removes its prior content. The extension replaces Pi's generic skill-reading paragraph and catalog only while `load_skill` is active. The replacement contains only the discovered skill names and descriptions. Durable routing policy is registered as `load_skill` tool prompt guidelines, so Pi includes it in the base system prompt rather than adding it through the per-turn hook: use `load_skill` at task start and material task or phase changes for direct matches, including matching parts of mixed tasks; perform only enough preliminary inspection to identify unclear work; follow loaded instructions and load required references before proceeding; and exclude merely adjacent skills or content already in context. Other tool metadata leads with the same loading action and describes parent inclusion and already-loaded notices. These are model instructions, not a runtime selection gate; deterministic tests cover prompt rendering and loader behavior, not model routing reliability. Install and update replace only a verified PUI-owned target; doctor hash-verifies all owned files and its CommonJS transaction module; uninstall preserves any modified or unrecognized target. Staged target scripts snapshot the complete prior directory before mutation, restore it on direct failure, and hand it to a transaction guard after target validation so an introducing update can roll back through an older release; the current transaction worker separately snapshots and restores the extension around approved updates.

PUI owns the exact package pins for its added extensions, but it does not manage their account state, logs, or optional fields except where listed above. For `rpiv-ask-user-question`, install and update replace only the three managed guidance leaves while preserving fields such as `collapseKey` and unknown guidance siblings. Doctor requires an exact guidance match. Uninstall checks both the absolute XDG and legacy paths, backs up each matching file, and removes the exact PUI-managed guidance leaves only while they still match the complete owned shape; user-modified guidance is preserved.

For `@99percentpeople/pi-background-tasks`, PUI replaces the pinned 2.1.1 bundle's 27 overlapping prompt guidelines and verbose tool/schema descriptions with six compact shared guidelines and concise per-tool metadata. It also preserves the bundle's named exports while routing each default extension-factory invocation through a fresh copy of the bundle body, isolating tasks, timers, persistence callbacks, widget context, and execution adapters between cached Pi runtimes. Within that isolated body it publishes session-scoped background activity under `globalThis[Symbol.for("pui.background-tasks.activity.v1")]`: `session_start` registers the active session ID with a predicate over its own running-task count, and `session_shutdown` removes the entry. Pi Web's patched session-running predicate consults that registry for the session ID, so a session that still owns running tasks is not treated as idle. The same body wraps every spawned PTY task so repeated `kill()` calls reach the native `node-pty` teardown at most once, because the pinned `node-pty` resolves `hpc` without clearing it and a second `ClosePseudoConsole` on the same handle corrupts the Windows heap. This prevents one session from replacing another session's snapshot appender with an unbound or wrong-session `pi.appendEntry()` closure. Because the transformed body no longer corresponds to the published source map, PUI removes the stale `sourceMappingURL`. The version-anchored transform is sentinel-marked and idempotent, fails closed on metadata, import/export, or source-map drift, is reapplied after each package reconciliation, and rebases its ownership artifacts onto the pristine bundle when `pi install` replaces the package for a new pinned version. Its hashed manifest records the pristine and patched bytes, allowing a later PUI-owned prompt revision to rebuild from the pristine backup without accepting user-modified output. Update transactions back up the bundle, original, and ownership manifest before mutation; staged target scripts retain this snapshot under one transaction-level guard until the enclosing worker reports success, so the introducing update remains reversible under an older installed worker. Doctor compares the installed bundle with the exact transform of its `index.min.js.pui-original`; uninstall restores that backup only while the installed output remains an exact PUI-owned match. The lifecycle entry points also verify that `node-pty` loads and approve/rebuild that dependency only when the bundled prebuild cannot load. For `@narumitw/pi-goal`, PUI preserves internal whitespace in new start objectives instead of rebuilding every parsed token with one ASCII space. The parser still recognizes the same subcommands and leading `--tokens` option, removes command-syntax quote delimiters, trims only the objective's outer whitespace, and leaves edit-command normalization unchanged. PUI also replaces the installed `formatStatus` bundle with a structured implementation that emits a readable `Goal: <status> · <reason> · <counter>` line (for example `Goal: paused · usage · 0/25`), with the counter omitted entirely when turns are unlimited. The completion path emits `Goal: complete · <elapsed>` before preserving upstream's eight-second status clear. PUI also defines an accepted `goal_complete.summary` as the complete user-facing response: it must include every deliverable required by the objective and concise verification where relevant rather than promise a later response. The patch removes upstream's 4,000-character schema cap, enforces Pi's 50 KB UTF-8 tool-output boundary at runtime, and never truncates accepted completion content. At `turn_end`, after Pi has persisted the accepted tool result, pi-goal first appends its hidden inactive contract and then emits the exact summary as an expanded durable `Goal complete` custom message with `triggerTurn: false`. Rejected completion calls are not promoted, no additional model request is made, and the original tool call remains under Process details. The replacement calls only cross-chunk imported helpers whose names the bundler preserves, never minified same-chunk locals. The patch is version-anchored to the pinned pi-goal release, marked with sentinel comments for idempotency, re-applied by install and update after every `pi install @narumitw/pi-goal`, and fails fast when its anchors drift so a version bump surfaces loudly instead of silently shipping an incomplete transform.

For `@gotgenes/pi-subagents`, PUI exposes exactly three built-in routes after a parallelism gate passes. `Explore` inspects code, Git revisions, and PRs with `read`, `bash`, `grep`, `find`, `ls`, and `load_skill`, using quick breadth when unspecified. Its `bash` access has no command whitelist and is not a read-only sandbox: the prompt permits inspection and temporary evidence artifacts but prohibits project edits, shared Git state changes, builds/tests, and external mutations. `Research` uses the file tools and `load_skill` plus `web_search`, `source_check`, `fetch_content`, and `get_search_content`, without shell access. `Worker` executes decided changes, builds, tests, and experiments with the seven upstream built-ins plus `load_skill`. Each child prompt states its exact tool set. Main retains critical-path execution, architecture, planning, judgment, synthesis, integration, verification, acceptance, verdicts, and the final response. Default delegation is permitted only when one substantial background track can run beside immediate substantial non-overlapping main work, or when at least two independent tracks can run concurrently; work is never invented merely to qualify. Each track receives one distinct deliverable with owned and excluded files, sources, or actions, expected evidence or output, and a stopping condition; a lone-child dispatch also names concurrent main work. Main completes that reserved work before waiting. Each evidence question or change has one owner. Shared files require distinct questions; otherwise the tracks merge. No parent or child duplicates an active track's investigation, edits, or checks, and main revalidates child evidence only after collection. Complexity, tool count, context volume, specialist fit, and local/external work type do not independently justify delegation. Before spawn or resume, main verifies the selected tools and inputs. Explore can retrieve named revisions through Git or a PR API without a prepared diff; shell retrieval alone no longer routes an investigation to Worker. Builds, tests, and experiments stay in main or use Worker after the gate. Naming a profile does not authorize foreground execution; foreground requires an explicit request. Sole-critical-path work stays in main, PUI built-ins default to background execution, and children are contractually forbidden from choosing, recommending, ranking, approving, or deciding; a decision-shaped prompt receives only supporting evidence with the decision marked out of scope.

For PUI's three built-ins, the child prompt builder preserves inherited authority and project instructions but removes the parent's generic full-capability role, tool catalog, tool-routing guidelines, and inherited skill catalog. The child resource loader then appends one skill catalog for the child session, avoiding duplicate skill metadata while keeping skills available. Explore resolves and cites exact revisions and reports retrieval failures rather than substituting the current checkout. It requires evidence or an explicit gap for every requested item, including relevant tests absent from a supplied diff. Full audits still cover every assigned file/hunk; an early finding does not end required coverage. Repeated scans need a named unresolved question, and evidence owned by another track is reported as a dependency rather than duplicated. Worker reports an unavailable empirical prerequisite instead of substituting a proposed experiment; Research treats local command, build, or test requirements as capability gaps. User-defined profiles retain upstream inheritance behavior.

Each Pi extension instance permits up to 128 running background agents and retains a FIFO queue of up to 512 additional agents; a further spawn fails before creating an agent record and can be retried after capacity becomes available. User settings cannot raise the running ceiling above 128. Foreground agents retain upstream behavior, bypass this background limiter, and are not selected by the default PUI routing policy. Parallel tracks may not overlap writes or other shared mutable state, depend on one another, or chain children. `max_turns` is a circuit breaker rather than task sizing and is set only when the user specifies it or current instructions supply an empirically calibrated value for that task class. Required results are collected before dependent work. Coverage evidence, not a runtime or child-reported completion label, establishes assignment completion. Errors, aborts, stopped or limit-steered outcomes, inaccessible evidence, missing status or coverage, and child-reported residual work remain incomplete until retried or reassigned with new evidence or direction after both gates still pass, or reported as a gap. Child prompts require every handoff field, using `none` when empty, including `complete`, `incomplete`, or `blocked` track status and unfinished coverage; this text is a handoff claim, not final acceptance. Worker uses the smallest sufficient evidence set and does not repeat equivalent scans once evidence suffices. Runtime result integrity is enforced separately: after a resolved turn loop PUI inspects the final assistant message, fails the child with the provider error plus any partial output when `stopReason` is `error`, and rejects an otherwise successful blank response, so neither can be recorded as `status: completed` with an empty result. A soft turn-limit wrap-up (`steered`) counts as terminal-incomplete rather than success and is labeled "Incomplete (turn limit)" in notifications and the result renderer. An explicit invocation `max_turns` overrides an agent-profile default. Explicit unknown types fail before a Worker can be selected. Built-in `general-purpose` and `Plan` are removed without aliases, but user-defined profiles with those names remain selectable. The `thinking` argument is schema-limited to Pi's six supported levels.

PUI delivers a background completion queued during an active parent run at the next `turn_end`, after rechecking whether the result was already consumed. It sends the extension's existing notification as a steering message, so the next parent turn sees the result without creating a second notification; a send failure remains queued and `agent_settled` retries it as the fallback. Before every parent model call, PUI replaces its prior hidden `pui-subagent-ledger` context projection with a fresh JSON record built directly from `SubagentManager`. The ledger includes every retained record in the current session—including terminal records—with its exact ID, description, lifecycle status, collected/uncollected result state, pending/reconciled parent state, and a status-specific next action. A collected result becomes reconciled mechanically only after it was already collected at the start of a later model turn and that turn completes; the tool-execution turn that collected it cannot mark it reconciled prematurely. Because this projection is rebuilt after compaction and never extracts IDs from transcript prose, repeated compactions retain authoritative handles without accumulating stale ledger messages or selecting IDs embedded by nested sessions. PUI also registers `abort_subagent`, which accepts one retained ID, stops queued work before it starts, requests cancellation of running work, and leaves completed or otherwise terminal records unchanged. Resume is ID-driven and must still pass the parallelism and capability gates: the parent supplies the retained agent ID and a new prompt, while ignored new-spawn type/model/reasoning/turn/background/context parameters are omitted. PUI also applies configurable default model and reasoning resolution. `~/.config/pui/subagents.json` contains parent-to-child mappings, initially mapping the exact parents `openai-codex/gpt-6-astra`, `openai-codex/gpt-5.6-sol`, and `openai-codex/gpt-5.6-terra` to `openai-codex/gpt-5.6-luna`. Custom mappings may still use fuzzy names. Parent keys, mapped children, and the subagent tool's explicit `model` argument all use the shared PUI resolver. If multiple keys resolve to the active parent, the invocation reports a configuration error; if the mapped child is unavailable, resolution falls back to the parent. An explicit invocation `model` wins over the mapping. An explicit invocation `thinking` also wins; when omitted, the child inherits the parent session's active reasoning level and Pi subsequently clamps it to the resolved child's capabilities. Agent-profile model and thinking defaults do not supersede these parented tool-invocation rules; none of the three PUI defaults hard-codes a model or reasoning level.

Users edit `modelMappings`; `_pui.defaultMappings` records the last defaults PUI offered so later updates can distinguish an untouched mapping from one the user changed or removed. Reconciliation compares mapping keys case-insensitively, preserves user key spelling, and rejects case-duplicate keys before they can resolve twice. A missing file means no mappings and falls back to the parent model; malformed configuration fails closed.

Install and update reconcile shipped defaults through the config's `_pui.defaultMappings` metadata. A newly shipped key is added, an untouched shipped value can be updated or retired, and a mapping the user changed or deleted is preserved. Unrelated fields also remain intact. PUI owns the installed default source, while supported user overrides and additions live in project `.pi/agents/*.md` or global `~/.pi/agent/agents/*.md`; lifecycle operations never mutate those files. Registry overlay is case-insensitive, so project profiles override global profiles and user profiles override PUI defaults regardless of filename case. An overridden built-in name is treated as custom: its listed user description and capabilities replace the PUI default route assumptions. New or changed profiles are reload-resolved immediately when named exactly; the parent-facing displayed profile catalog refreshes on the next session. Custom profiles are selected only when the user names one or its listed description is the best match, and their prompts state task, scope, constraints, listed capabilities, success criteria, and output without assuming unlisted tools.

The version-anchored source transform is sentinel-marked and idempotent, fails closed on version, metadata, schema, or unknown ownership-revision drift, and is reapplied after package reconciliation. Exact prior revisions, including revision 14, migrate from pristine backups to revision 15. The revision 15 tests exercise tool configuration, rendered prompt contracts, and migration/restoration; routing scenarios are evaluation cases, not evidence of live-model compliance. Behavioral efficacy of the revised guidance remains unverified. Artifact and snapshot writes use same-directory temporary files plus atomic rename. A durable package-local journal restores an interrupted patch or restore before the next lifecycle mutation, while update transactions retain the outer snapshot until validation succeeds; an already-current patch performs no source/manifest rewrite. Doctor validates both the user mapping schema and the installed transform. Uninstall supports every exact known owned revision, restores backups only when the pinned package identity and installed files still match that PUI-owned shape, and leaves user profiles and mapping config in place.

PUI's reasoning-summary patch applies to any model using the managed OpenAI, Azure OpenAI, or Codex Responses adapters; it does not inspect or restrict the provider name. During streaming, the provider parser keeps validated summary deltas in a separate transient buffer, so raw reasoning in the normal thinking buffer cannot become display text. The transient `puiReasoningSummaryText` marker is accepted only by an explicitly live streaming projection. Final, persisted, deferred, and exported messages are projected only from signatures containing a non-empty array made entirely of string `summary_text` entries. The render-only projection leaves original thinking blocks, encrypted replay content, signatures, grouping, persistence, and token accounting intact. It applies to Pi Web's transcript, reconnect event stream, previews, deferred history endpoint, context loading, and HTML export, plus standalone Pi's TUI and HTML export. Pi Web loads thinking on demand, so the deferred-thinking endpoint returns the projected summary text for a summary block and the stored provider thinking for every block the projection leaves as a thinking block; non-Responses APIs therefore keep their reasoning text while an untrusted Responses block still yields no content. The same Pi Web projection strictly recognizes pi-goal's owned initial and explicit-resume prompt shapes and displays canonical `/goal …` or `/goal resume` text without changing stored prompts or model context; continuations and other generated goal messages are unchanged. Pi Web identifies a pending optimistic goal start, edit, or resume from its existing message key. Its slash-command `prompt_done` retains that key and defers transcript reload and UI settlement until the generated goal user message reconciles it, independent of whether `agent_start` arrives before or after `prompt_done`. If a command does not produce a turn, Pi Web's existing server-state settlement path performs the authoritative idle reload. A summary whose complete Markdown content is bold has its enclosing bold markers converted to italic markers, including multiline and multi-paragraph summaries; mixed emphasis remains unchanged. Non-Responses APIs retain upstream behavior.

In Pi Web, `subagent-notification` custom-message cards retain their existing color and header but start as a single tool-like row with the timestamp immediately left of a chevron. As with tool rows, clicking anywhere on the header—or focusing it and pressing Enter or Space—toggles expansion. Expanding restores the existing content, Copy action, and Details action; collapsing hides those rows again. When an extension starts a run while Pi Web is reconnecting, the client schedules one persisted-transcript reload and performs it at the first assistant snapshot, after the custom prompt has been persisted, so that prompt is not lost in the connection gap or by a reconciliation race. The slash command's own `prompt_done` event does not start a competing stale transcript reload while its optimistic goal command remains pending, even when `agent_start` has not arrived yet. A replayed user-message start cancels the pending reload, narrowing reconciliation away from ordinary UI-started runs. The visible `Goal complete` custom-message body is forced expanded even when live transcript reconciliation reuses a custom-message component that was previously collapsed. It alone reuses Pi Web's existing compaction Markdown class, giving it the 1.5 line height and paragraph, heading, list, quote, table, and code spacing intended for long summary content; its generic custom-message card and controls remain unchanged. Other custom-message types keep their upstream initial expansion behavior and presentation.

The same exact-version Pi Web display transform adds an ID-card **Copy ID** button immediately before **Full history** in the session toolbar. It uses Pi Web's existing clipboard helper and active session identity, remains disabled until a saved session exists, and retains native button keyboard behavior and an accessible name. After a successful copy, an `aria-live` label changes to **Copied!** for exactly three seconds. Fixed desktop button and label widths prevent either state from shifting adjacent controls; the compact toolbar keeps the same icon-only width.

The exact-version transform patches only runtime-loaded compiled artifacts. It runs after branding because both transforms touch Pi Web page bundles, then versions browser references from the final display-patched client bytes so stale browser code cannot remain cached; uninstall removes it before restoring branding. Its toolbar transform requires exactly one clipboard helper and one structurally matched session-toolbar seam in both server and client bundles, failing closed on drift rather than guessing at a nearby button. Hashed manifests and distinct `.pui-reasoning-original` sidecars support verification, npm reconciliation, migration from an older verified PUI revision, checked removal, and cross-runtime rollback. Snapshot restoration preflights live artifact bytes, replaces files atomically, and rewinds already-restored artifacts if a later restore operation fails; invalid snapshot evidence and restore I/O failures are reported separately. Staged updates retain a snapshot until the outer transaction reports success, including when the installed worker predates this patch.

PUI's Pi #8782 backport is a temporary exact-version compatibility shim for the runtime used by Pi Web. Pi 0.84.3 can let a completed tool result cross the normal threshold before the next provider request; PUI's helper backports only upstream PR #8782's agent-loop scheduling and AgentSession between-turn compaction into the resolved unbundled Pi Web dependency tree. It does not patch the standalone bundled `pi` CLI (`dist/bundle/cli.js`), change compaction thresholds, add a new dependency, build Pi, or include the upstream TUI progress-indicator hunk. The standalone CLI therefore remains stock 0.84.3 while Pi Web uses 0.84.3 plus this backport. The helper resolves private packages from Pi Web rather than guessing a global path, requires the exact `@agegr/pi-web` 0.8.11 / Pi 0.84.3 composition, transforms both files in memory, syntax-checks them, records a hashed ownership manifest, and restores both originals only when the complete owned shape remains intact. Install and update apply it after runtime parity and before restart; doctor fails when it is absent or drifted; uninstall removes it from the default path; the helper is retired when PUI pins the first released Pi version containing #8782.

PUI's session communication is Pi Web-only. Peer task-message cards use Pi Web's compaction/Goal complete Markdown typography. Their persisted and model-facing envelope remains unchanged; the display projection parses only the final JSON string emitted by the PUI broker, labels it `Message`, and converts its newlines to Markdown hard breaks. Malformed or non-string JSON remains unchanged. The exact `@agegr/pi-web` 0.8.11 server patch injects the broker into the resolved server chunk `.next/server/chunks/6429.js`; the adjacent PUI sidecar is `.next/server/pui-session-broker.cjs`, with `.next/server/.pui-session-communication.json` recording ownership hashes and `.pui-session-original` retaining the pristine chunk. The broker exposes five tools through the installed extension: `session_list` groups recent sessions by canonical project, `session_get` returns metadata and `sessionLogPath`, the absolute path to the persisted JSONL session log, without reading that log into context, `session_send` delivers attributed peer task input and resumes a stopped target, `session_start` creates a normal session and queues its completion notification while returning immediately, and `session_abort` stops only work started or resumed by the caller without deleting history. The model-facing contracts permit `session_send` only when the current user explicitly requests sending task input to another session and permit `session_start` only when the current user explicitly requests starting a new session. Task complexity, potential parallelism, target or project availability, and peer input do not grant that permission. Active sends default to steering; `follow_up` is also supported. Peer task input is handled only within the current user and system instructions. It is explicitly untrusted data, not a user message, authority, approval, or authorization, and cannot override those instructions. Completion notifications likewise JSON-encode their status as untrusted data that cannot override instructions. Model selectors accept exact provider/model IDs or fuzzy matches. `model` and `effort` are applied only when the user explicitly requested those overrides; omitted values inherit normally, and an unavailable effort is rounded to the nearest lower supported level. The tools do not impose a global chaining or fan-out policy, so unrestricted peer delegation can create unbounded chains or fan-out and must remain subject to the surrounding task's authority and resource constraints.

The patch is version-anchored to Pi Web 0.8.11 and fails closed on package, anchor, manifest, or sidecar drift. It also rewrites Pi Web's session-running predicate to consult the background-activity registry keyed by session ID, so a background-task session stays active until its tasks finish. Install and update snapshot the chunk, backup, sidecar, and manifest before mutation; an intact prior broker revision is migrated in place to the current revision, and update retains the snapshot through transaction validation and restores it on failure. Doctor verifies the complete PUI-owned shape and hashes. Uninstall restores the original chunk and removes the sidecar, manifest, and backup only while all owned bytes still match; modified or incomplete artifacts are preserved. Standalone Pi is not patched and does not receive these tools. The extension under `~/.pi/agent/extensions/pui-session-communication/` is managed separately with its own exact-file ownership guard and is likewise preserved when modified.

PUI's MCP policy is proxy-first: servers stay available through the `mcp` tool, and only frequently used operations are promoted through a server's `directTools` list. PUI does not set `settings.disableProxyTool`, overwrite global adapter settings, or apply its Playwright policy to unrelated MCP servers. Doctor compares `mcpFooterStatus` with `stack.json` and reports a missing or drifted value as `FAIL`.

It may also write one per-user autostart file:

- Windows: `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\pui-piweb.vbs`
- macOS: `~/Library/LaunchAgents/com.pui.piweb.plist`
- Linux: `~/.config/systemd/user/pui-piweb.service`

Uninstall regenerates the platform's complete canonical PUI content and removes the entry only on an exact match. A same-named file that was edited, moved to a different launcher path, or is otherwise unrecognized is preserved with a warning.

The branding helper patches only Pi Web's top-level title, description, sidebar brand, manifest, favicon, Apple touch icon, and PWA icon metadata. Component-name occurrences such as release text remain “Pi Web.” It also shrinks the footer widget-trigger cell from its fixed 70% shelf basis to content width (keeping the 70% cap and horizontal scroll) so a single extension widget does not leave a large empty gap next to the status text, and drops the now-adjacent duplicate right border on the last trigger. The helper also extends the Pi Web tool-call header summary: upstream recognizes only bash/read-style argument names and otherwise stringifies the first argument, which displays a `load_skill` reference load identically to its skill load; the identifier-agnostic transform inserts a `name`-plus-`reference` branch into both the client page chunk and the server page bundle so the header shows `skill: ref1, ref2` for reference loads. Original build files are stored as `*.pui-original`, the service-worker cache name receives a PUI suffix, update reapplies the override, and uninstall restores the originals.

The update integration is pinned to the exact Pi Web version in `stack.json`. It replaces the existing `/api/app-update` implementation through a narrow expected-pattern check and injects one public client script into the prerendered app document. Apply and removal snapshot every owned artifact, change the ownership manifest last, and compensate back to the pre-operation bytes if an intermediate write or deletion fails. Its separate ownership manifest and backups allow uninstall to restore it only while the complete installed shape still matches PUI.

The injected client renders the update notification card and an always-visible Restart PUI control (reusing the card styling, positioned below the notification). Restart sends `PUT /api/app-update`; the bridge rejects the request with HTTP 409 while an update or restart is already in progress, marks the status as restarting, then spawns a detached restarter that stops the managed Pi Web processes and relaunches Pi Web through the managed service on macOS (`launchctl kickstart -k`) or Linux (`systemctl --user restart`). On Windows, the restart worker verifies the canonical Startup-folder VBS and launches it through Windows Script Host. The VBS starts `%APPDATA%\npm\pi-web.cmd --no-open` with window style `0`, so Pi Web and its Next.js child inherit a hidden console. Detaching `cmd.exe` itself does not provide that guarantee because the Node process started later by the npm shim can allocate a new visible console. The worker's HTTP health gate observes whether the asynchronous VBS launch succeeds. Unmanaged POSIX installs fall back to detached `pi-web --no-open`. The restarter writes progress to the update status file and only reports success after Pi Web answers HTTP again. The client shows the restart phases on the card: on success the page reloads (returning an active Restart control); on failure the card reports the error and the button is re-enabled. A completed restart is consumed once and removed before normal release discovery resumes. If another tab consumes that one-shot result first, the requesting tab treats the next ordinary healthy response after observed restart progress as successful recovery instead of waiting 90 seconds. Retained restart failures remain actionable after reload. Before any bridge action loads `updater.js`, the bridge verifies the manifest's exact four-file extension shape and every recorded SHA-256. Detached update and restart workers carry a mandatory identity-check marker and repeat the same adjacent-manifest verification before executing; missing, extra, or drifted installed files fail closed. The marker applies only to those installed workers: staged release scripts and the `standalone-busy` idle gate they spawn run without it, because a release tree has no adjacent certified manifest. The restarter runs from the installed `updater.js` and never goes through the update transaction's idle gate.

Autostart suppresses Pi Web's npm updater because PUI owns the complete pinned composition. The PUI card checks the latest stable GitHub release once per app launch. After explicit approval, a detached worker stages tagged snapshots in OS temporary storage, waits for managed work to become idle, applies the target, and rolls back to the previous manifest-defined composition on failure. An unreachable Pi Web activity endpoint permits recovery only when process inspection confirms no managed Pi Web process exists; otherwise the idle gate fails closed. Pi Web process detection reads the process snapshot and matches the installed package path or the npm bin shim, because name-based matching misses the launchd-spawned agent, and it stops the process holding the Pi Web port when the retitled Next.js child would otherwise survive.

Target and rollback script output is retained at `~/.pi/agent/state/pui-update/last.log` (`%USERPROFILE%\.pi\agent\state\pui-update\last.log` on Windows), and every status write is mirrored to `last-status.json` beside it, so an interrupted update stays diagnosable after a reboot. Transaction status used by the running app remains in OS temporary storage and survives only long enough for the app to report the result.

Both lifecycle scripts stop Pi Web before mutating global packages and restart it only in the final step, so an abort in between is repaired from the exit path: the LaunchAgent is loaded or kickstarted, the systemd user unit is started, or a manually started `pi-web --no-open` is relaunched, each followed by an HTTP 200 gate. The updater worker also falls back from `launchctl kickstart` to `launchctl load` and reports the launcher command, exit code, and stderr through the update status. When an older rollback script completes restoration but fails at its obsolete restart boundary, the current worker relaunches Pi Web and accepts recovery only after the prior certified identity and live bridge validate.

The update dialog stops polling instead of claiming progress forever: it keeps waiting while transaction status keeps arriving, and after 15 status-free responses or 15 minutes without a response it reports the outcome as unknown with Reload and Keep waiting actions.
