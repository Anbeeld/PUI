# PUI patches

PUI owns the configuration and targeted patches that make its upstream components work as one reproducible application without a Pi fork. The [component reference](components.md) lists upstream packages and repository structure.

## Managed files and fields

PUI makes timestamped backups before inspecting or changing existing configuration JSON. It structurally merges the owned fields below except for `~/.config/pui/reasoning-summaries.json` and `~/.config/pui/session-titles.json`, whose create-only lifecycles are documented separately. The native recovery path also backs up `~/.pi/agent/npm/package.json` before asking npm to record its exact `node-pty` script approval:

- `~/.pi/agent/settings.json`: `defaultTools`, managed package entries, and explicitly retired package entries
- `~/.pi/web-search.json`: `searchRouting`, `fetchRouting`, and `workflow`
- `~/.config/mcp/mcp.json`: `mcpServers.playwright.command`, `args`, `lifecycle`, the six-tool `directTools` policy, and `settings.mcpFooterStatus`
- `~/.pi/agent/pi-goal.json`: `continuationLimits.automaticTurns` and `continuationLimits.noProgressTurns`
- `~/.config/rpiv-ask-user-question/config.json`: exact `guidance.description`, `guidance.promptSnippet`, and `guidance.promptGuidelines` values; an existing absolute `$XDG_CONFIG_HOME/rpiv-ask-user-question/config.json` takes precedence
- `~/.pi/agent/npm/package.json`: only the exact `node-pty` lifecycle approval when a native rebuild is required
- `~/.pi/agent/npm/node_modules/@99percentpeople/pi-background-tasks/index.min.js`: exact PUI-owned tool metadata plus per-extension-instance runtime-state isolation; the upstream bundle is retained as `index.min.js.pui-original` and ownership hashes as `index.min.js.pui-manifest.json`
- `~/.pi/agent/npm/node_modules/@gotgenes/pi-subagents/` sources listed by `stack.json.subagentsPromptPatch.files`: exact PUI-owned taxonomy, routing guidance, child-prompt inheritance filtering, capability allowlists, unknown-type handling, per-instance running/queued limits, result-integrity, mapped-model, parent-reasoning, and completion-delivery policy; each upstream file is retained as `<file>.pui-original` and ownership hashes as `.pui-subagents-prompt-manifest.json`
- `~/.config/pui/subagents.json`: user-editable fuzzy model mappings plus `_pui.defaultMappings` reconciliation metadata; updates preserve user changes and deletions while adding newly shipped defaults
- `~/.config/pui/reasoning-summaries.json`: create-only user configuration with `schemaVersion: 1` and a `modelModes` object; a missing file receives the three `gpt-5.6-*` `detailed` defaults, while any existing valid file remains byte-for-byte unchanged
- `~/.config/pui/session-titles.json`: create-only user configuration with `schemaVersion: 1` and an ordered `models` array of exact `provider/model-id` or fuzzy selectors; new files start with an empty list and use the active session model
- Pi Web's resolved unbundled `node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.js` and `@earendil-works/pi-agent-core/dist/agent-loop.js`: temporary exact Pi #8782 runtime backport; originals are retained beside the targets as `*.pui-8782-original` and ownership hashes as `.pui-pi-8782-backport.json`
- Exact Pi Web and standalone Pi compiled display/provider seams selected by `pui-reasoning-summary-patch.js` under the version and ownership policy in `reasoningSummaryPatch`: Responses reasoning-summary compatibility for any model using the managed Responses adapters, canonical Pi Web goal-command display, compaction-style typography for visible `Goal complete` bodies, and collapsed-by-default Pi Web subagent notifications; originals use `.pui-reasoning-original` and each runtime root records hashes in `.pui-reasoning-summary.json`
- `~/.pi/agent/extensions/pui-update/`: installed PUI identity and detached transaction worker
- `~/.pi/agent/extensions/pui-skill-loader/`: exact PUI-owned `load_skill` extension source, package metadata, and hash manifest
- `~/.pi/agent/extensions/pui-reasoning-summary/`: exact PUI-owned Responses request-policy extension source, package metadata, and hash manifest
- `~/.pi/agent/extensions/pui-session-title/`: exact PUI-owned automatic-title extension source, package metadata, and hash manifest

The reasoning-summary extension handles request generation separately from `pui-reasoning-summary-patch.js`, which remains responsible for safe parsing and display. On `before_provider_request`, it uses `ctx.model.api`, `ctx.model.provider`, and `ctx.model.id`; it never trusts the payload's model field. It is restricted to `openai-responses`, `azure-openai-responses`, and `openai-codex-responses`. An exact `provider/model-id` configuration key wins over an exact bare `model-id`. Modes `auto`, `concise`, and `detailed` set `reasoning.summary`; `none` removes it. A missing or invalid configuration, unsupported API, unknown model, absent reasoning object, or `effort: "none"` leaves the payload unchanged.

The default file is:

```json
{
  "schemaVersion": 1,
  "modelModes": {
    "gpt-5.6-sol": "detailed",
    "gpt-5.6-terra": "detailed",
    "gpt-5.6-luna": "detailed"
  }
}
```

Install and update create that file only when missing. Existing valid content—including changed values, removed entries, additional valid entries, formatting, and unknown top-level fields—is preserved byte-for-byte. Existing invalid content is backed up, is not overwritten, and stops the lifecycle operation. Doctor validates the schema. Uninstall preserves the configuration. The installed extension itself uses exact manifest hashes: install/update replace only a verified PUI-owned target, doctor verifies it, uninstall preserves drift, and update rollback restores the complete previous directory.

The session-title extension listens at Pi's `before_agent_start` seam. For a new unnamed session with no prior substantive text, it marks the attempt synchronously and detaches generation so the main agent starts without waiting. It uses the expanded first prompt's text only; image-only turns do not consume the one attempt. Fenced code or logs are removed when surrounding prose is available, whitespace is collapsed, and the remaining input is limited to 600 Unicode code points using both the beginning and end. The request is one user message whose input is embedded as a JSON string, with no system prompt, tools, session history, or session cache identifier. It directly prohibits reasoning and explanation, requests `reasoningEffort: "none"` when supported, and otherwise selects the first supported level in `minimal`, `low`, `medium`, `high`, `xhigh`, `max` order from the model's reasoning metadata. It uses a 1,024-token output ceiling, a ten-second provider timeout, two provider retries, and a 30-second overall deadline that also aborts with the run or session shutdown.

Configured model selectors are resolved in order using the same exact-then-fuzzy scoring policy as PUI's subagent integration. Unavailable selectors are skipped, duplicate resolved provider/model pairs are removed, at most four configured models are tried, and the active session model is appended as the final fallback. The first successful non-empty text response is stripped of thinking blocks, terminal control sequences, title tags or labels, wrapping quotes or backticks, extra lines, whitespace, and ending punctuation, then capped at 80 Unicode code points and rejected when nothing alphanumeric remains. Empty, aborted, deferred, or failed responses advance to the next candidate. Complete failure is silent. Immediately before persistence, the extension rechecks the in-memory session name, its own session-info events, and the persisted session file so an explicit or concurrent manual name—including a Pi Web rename written through a separate session manager—wins.

The default file is:

```json
{
  "schemaVersion": 1,
  "models": []
}
```

For example, `"models": ["openai-codex/gpt-5.6-luna", "haiku"]` tries the exact available Luna identity first, then the best available fuzzy Haiku match, then the active session model. Install and update create the file only when missing; valid existing bytes and unknown top-level fields are preserved. Invalid content is backed up without overwrite and stops the lifecycle operation. Doctor validates both configuration and extension identity, uninstall preserves the configuration and any drifted extension directory, and update transactions restore or remove the extension according to its prior state.

The skill-loader extension keeps Pi's discovered skill names and descriptions in the system prompt as routing metadata. When `load_skill({ name })` is called, it resolves only an exact discovered name, rejects files over 50 KB or 2,000 lines without returning partial content, and returns the skill body with its directory plus a sorted list of direct regular `references/*.md` files. `load_skill({ name, reference })` accepts one or more listed filenames with or without `.md` as a single value or a list, rejects paths, traversal, non-Markdown files, symlinks, and unavailable references, and validates a whole list before loading anything. If the parent skill's tool result is absent from active context, the same result includes the skill body before the requested reference bodies. A batched load returns one structured result: the optional parent skill, a summary naming newly loaded and already loaded references, then each loaded reference body under its own heading, with the combined output bounded by the same limits. Context-derived ownership keeps duplicate loads idempotent while permitting the skill or a reference to reload after compaction or tree navigation removes its prior content. The extension replaces Pi's generic skill-reading paragraph only while `load_skill` is active. The replacement directs the model to use `load_skill` at task start and material task or phase changes for direct matches, including matching parts of mixed tasks. It permits only enough preliminary inspection to identify unclear work, requires following loaded instructions and loading their required references before proceeding, and retains the exclusions for merely adjacent skills and content already in context. Tool metadata leads with the same loading action and describes parent inclusion and already-loaded notices. These are model instructions, not a runtime selection gate; deterministic tests cover prompt rendering and loader behavior, not model routing reliability. Install and update replace only a verified PUI-owned target; doctor hash-verifies all owned files and its CommonJS transaction module; uninstall preserves any modified or unrecognized target. Staged target scripts snapshot the complete prior directory before mutation, restore it on direct failure, and hand it to a transaction guard after target validation so an introducing update can roll back through an older release; the current transaction worker separately snapshots and restores the extension around approved updates.

PUI owns the exact package pins for its added extensions, but it does not manage their account state, logs, or optional fields except where listed above. For `rpiv-ask-user-question`, install and update replace only the three managed guidance leaves while preserving fields such as `collapseKey` and unknown guidance siblings. Doctor requires an exact guidance match. Uninstall checks both the absolute XDG and legacy paths, backs up each matching file, and removes the exact PUI-managed guidance leaves only while they still match the complete owned shape; user-modified guidance is preserved.

For `@99percentpeople/pi-background-tasks`, PUI replaces the pinned 2.1.1 bundle's 27 overlapping prompt guidelines and verbose tool/schema descriptions with six compact shared guidelines and concise per-tool metadata. It also preserves the bundle's named exports while routing each default extension-factory invocation through a fresh copy of the bundle body, isolating tasks, timers, persistence callbacks, widget context, and execution adapters between cached Pi runtimes. This prevents one session from replacing another session's snapshot appender with an unbound or wrong-session `pi.appendEntry()` closure. Because the transformed body no longer corresponds to the published source map, PUI removes the stale `sourceMappingURL`. The version-anchored transform is sentinel-marked and idempotent, fails closed on metadata, import/export, or source-map drift, is reapplied after each package reconciliation, and rebases its ownership artifacts onto the pristine bundle when `pi install` replaces the package for a new pinned version. Its hashed manifest records the pristine and patched bytes, allowing a later PUI-owned prompt revision to rebuild from the pristine backup without accepting user-modified output. Update transactions back up the bundle, original, and ownership manifest before mutation; staged target scripts retain this snapshot under one transaction-level guard until the enclosing worker reports success, so the introducing update remains reversible under an older installed worker. Doctor compares the installed bundle with the exact transform of its `index.min.js.pui-original`; uninstall restores that backup only while the installed output remains an exact PUI-owned match. The lifecycle entry points also verify that `node-pty` loads and approve/rebuild that dependency only when the bundled prebuild cannot load. For `@narumitw/pi-goal`, PUI preserves internal whitespace in new start objectives instead of rebuilding every parsed token with one ASCII space. The parser still recognizes the same subcommands and leading `--tokens` option, removes command-syntax quote delimiters, trims only the objective's outer whitespace, and leaves edit-command normalization unchanged. PUI also replaces the installed `formatStatus` bundle with a structured implementation that emits a readable `Goal: <status> · <reason> · <counter>` line (for example `Goal: paused · usage · 0/25`), with the counter omitted entirely when turns are unlimited. The completion path emits `Goal: complete · <elapsed>` before preserving upstream's eight-second status clear. PUI also defines an accepted `goal_complete.summary` as the complete user-facing response: it must include every deliverable required by the objective and concise verification where relevant rather than promise a later response. The patch removes upstream's 4,000-character schema cap, enforces Pi's 50 KB UTF-8 tool-output boundary at runtime, and never truncates accepted completion content. At `turn_end`, after Pi has persisted the accepted tool result, pi-goal first appends its hidden inactive contract and then emits the exact summary as an expanded durable `Goal complete` custom message with `triggerTurn: false`. Rejected completion calls are not promoted, no additional model request is made, and the original tool call remains under Process details. The replacement calls only cross-chunk imported helpers whose names the bundler preserves, never minified same-chunk locals. The patch is version-anchored to the pinned pi-goal release, marked with sentinel comments for idempotency, re-applied by install and update after every `pi install @narumitw/pi-goal`, and fails fast when its anchors drift so a version bump surfaces loudly instead of silently shipping an incomplete transform.

For `@gotgenes/pi-subagents`, PUI exposes exactly three built-in routes after a parallelism gate passes. `Explore` establishes local repository evidence with `read`, `grep`, `find`, `ls`, and `load_skill`, and uses quick breadth when unspecified; `Research` adds `web_search`, `source_check`, `fetch_content`, and `get_search_content`; `Worker` executes decided work with the seven upstream built-ins plus `load_skill`. Each child prompt states its exact allowlist. Main retains critical-path execution, architecture, planning, judgment, synthesis, integration, verification, acceptance, verdicts, and the final response. Default delegation is permitted only when one substantial background track can run beside immediate substantial non-overlapping main work, or when at least two independent tracks can run concurrently; work is never invented merely to qualify. Each track receives one distinct deliverable with owned and excluded files, sources, or actions, expected evidence or output, and a stopping condition; a lone-child dispatch also names concurrent main work. Main completes that reserved work before waiting. Shared topics, files, sources, or access do not establish independence, and no parent or child duplicates an active track's evidence gathering, edits, or checks. Complexity, tool count, context volume, specialist fit, and local/external work type do not independently justify delegation. Before spawn or resume, main verifies the selected tools and readable inputs; named revisions require supplied diff text or a readable checkout for Explore or Research, while local Git, builds, tests, and generated experiments stay in main or use Worker after the gate. Naming a profile does not authorize foreground execution; foreground requires an explicit request. Sole-critical-path work stays in main, PUI built-ins default to background execution, and children are contractually forbidden from choosing, recommending, ranking, approving, or deciding; a decision-shaped prompt receives only supporting evidence with the decision marked out of scope.

For PUI's three built-ins, the child prompt builder preserves inherited authority and project instructions but removes the parent's generic full-capability role, tool catalog, tool-routing guidelines, and inherited skill catalog. The child resource loader then appends one skill catalog for the child session, avoiding duplicate skill metadata while keeping skills available. Explore checks evidence accessibility before searching, never treats one revision as evidence for another, and stops instead of reconstructing unavailable revisions from Git internals, caches, generated trees, or unrelated scratch directories. Worker reports an unavailable empirical prerequisite instead of substituting a proposed experiment; Research treats local command, build, or test requirements as capability gaps. User-defined profiles retain upstream inheritance behavior.

Each Pi extension instance permits up to 128 running background agents and retains a FIFO queue of up to 512 additional agents; a further spawn fails before creating an agent record and can be retried after capacity becomes available. User settings cannot raise the running ceiling above 128. Foreground agents retain upstream behavior, bypass this background limiter, and are not selected by the default PUI routing policy. Parallel tracks may not overlap writes or other shared mutable state, depend on one another, or chain children. `max_turns` is a circuit breaker rather than task sizing and is set only when the user specifies it or current instructions supply an empirically calibrated value for that task class. Required results are collected before dependent work and matched against their deliverables and required fields. Errors, aborts, stopped or limit-steered outcomes, inaccessible evidence, missing status or coverage, and child-reported residual work remain incomplete until retried or reassigned with new evidence or direction after both gates still pass, or reported as a gap. Child prompts require every handoff field, using `none` when empty, including `complete`, `incomplete`, or `blocked` track status and unfinished coverage; this text is a handoff claim, not final acceptance. Worker uses the smallest sufficient evidence set and does not repeat equivalent scans once evidence suffices. Runtime result integrity is enforced separately: after a resolved turn loop PUI inspects the final assistant message, fails the child with the provider error plus any partial output when `stopReason` is `error`, and rejects an otherwise successful blank response, so neither can be recorded as `status: completed` with an empty result. A soft turn-limit wrap-up (`steered`) counts as terminal-incomplete rather than success and is labeled "Incomplete (turn limit)" in notifications and the result renderer. An explicit invocation `max_turns` overrides an agent-profile default. Explicit unknown types fail before a Worker can be selected. Built-in `general-purpose` and `Plan` are removed without aliases, but user-defined profiles with those names remain selectable. The `thinking` argument is schema-limited to Pi's six supported levels.

PUI delivers a background completion queued during an active parent run at the next `turn_end`, after rechecking whether the result was already consumed. It sends the extension's existing notification as a steering message, so the next parent turn sees the result without creating a second notification; a send failure remains queued and `agent_settled` retries it as the fallback. Resume is ID-driven and must still pass the parallelism and capability gates: the parent supplies the retained agent ID and a new prompt, while ignored new-spawn type/model/reasoning/turn/background/context parameters are omitted. PUI also applies configurable default model and reasoning resolution. `~/.config/pui/subagents.json` contains parent-to-child mappings, initially mapping the exact parents `openai-codex/gpt-6-astra`, `openai-codex/gpt-5.6-sol`, and `openai-codex/gpt-5.6-terra` to `openai-codex/gpt-5.6-luna`. Custom mappings may still use fuzzy names. Both sides use the same exact-then-fuzzy resolver as the subagent tool's explicit `model` argument. If multiple keys resolve to the active parent, the invocation reports a configuration error; if the mapped child is unavailable, resolution falls back to the parent. An explicit invocation `model` wins over the mapping. An explicit invocation `thinking` also wins; when omitted, the child inherits the parent session's active reasoning level and Pi subsequently clamps it to the resolved child's capabilities. Agent-profile model and thinking defaults do not supersede these parented tool-invocation rules; none of the three PUI defaults hard-codes a model or reasoning level.

Users edit `modelMappings`; `_pui.defaultMappings` records the last defaults PUI offered so later updates can distinguish an untouched mapping from one the user changed or removed. Reconciliation compares mapping keys case-insensitively, preserves user key spelling, and rejects case-duplicate keys before they can resolve twice. A missing file means no mappings and falls back to the parent model; malformed configuration fails closed.

Install and update reconcile shipped defaults through the config's `_pui.defaultMappings` metadata. A newly shipped key is added, an untouched shipped value can be updated or retired, and a mapping the user changed or deleted is preserved. Unrelated fields also remain intact. PUI owns the installed default source, while supported user overrides and additions live in project `.pi/agents/*.md` or global `~/.pi/agent/agents/*.md`; lifecycle operations never mutate those files. Registry overlay is case-insensitive, so project profiles override global profiles and user profiles override PUI defaults regardless of filename case. An overridden built-in name is treated as custom: its listed user description and capabilities replace the PUI default route assumptions. New or changed profiles are reload-resolved immediately when named exactly; the parent-facing displayed profile catalog refreshes on the next session. Custom profiles are selected only when the user names one or its listed description is the best match, and their prompts state task, scope, constraints, listed capabilities, success criteria, and output without assuming unlisted tools.

The version-anchored source transform is sentinel-marked and idempotent, fails closed on version, metadata, schema, or unknown ownership-revision drift, and is reapplied after package reconciliation. Exact prior revisions migrate from pristine backups. Artifact and snapshot writes use same-directory temporary files plus atomic rename. A durable package-local journal restores an interrupted patch or restore before the next lifecycle mutation, while update transactions retain the outer snapshot until validation succeeds; an already-current patch performs no source/manifest rewrite. Doctor validates both the user mapping schema and the installed transform. Uninstall supports every exact known owned revision, restores backups only when the pinned package identity and installed files still match that PUI-owned shape, and leaves user profiles and mapping config in place.

PUI's reasoning-summary patch applies to any model using the managed OpenAI, Azure OpenAI, or Codex Responses adapters; it does not inspect or restrict the provider name. During streaming, the provider parser keeps validated summary deltas in a separate transient buffer, so raw reasoning in the normal thinking buffer cannot become display text. The transient `puiReasoningSummaryText` marker is accepted only by an explicitly live streaming projection. Final, persisted, deferred, and exported messages are projected only from signatures containing a non-empty array made entirely of string `summary_text` entries. The render-only projection leaves original thinking blocks, encrypted replay content, signatures, grouping, persistence, and token accounting intact. It applies to Pi Web's transcript, reconnect event stream, previews, deferred history endpoint, context loading, and HTML export, plus standalone Pi's TUI and HTML export. The same Pi Web projection strictly recognizes pi-goal's owned initial and explicit-resume prompt shapes and displays canonical `/goal …` or `/goal resume` text without changing stored prompts or model context; continuations and other generated goal messages are unchanged. Pi Web identifies a pending optimistic goal start, edit, or resume from its existing message key. Its slash-command `prompt_done` retains that key and defers transcript reload and UI settlement until the generated goal user message reconciles it, independent of whether `agent_start` arrives before or after `prompt_done`. If a command does not produce a turn, Pi Web's existing server-state settlement path performs the authoritative idle reload. A summary whose complete Markdown content is bold has its enclosing bold markers converted to italic markers, including multiline and multi-paragraph summaries; mixed emphasis remains unchanged. Non-Responses APIs retain upstream behavior.

In Pi Web, `subagent-notification` custom-message cards retain their existing color and header but start as a single tool-like row with the timestamp immediately left of a chevron. As with tool rows, clicking anywhere on the header—or focusing it and pressing Enter or Space—toggles expansion. Expanding restores the existing content, Copy action, and Details action; collapsing hides those rows again. When an extension starts a run while Pi Web is reconnecting, the client schedules one persisted-transcript reload and performs it at the first assistant snapshot, after the custom prompt has been persisted, so that prompt is not lost in the connection gap or by a reconciliation race. The slash command's own `prompt_done` event does not start a competing stale transcript reload while its optimistic goal command remains pending, even when `agent_start` has not arrived yet. A replayed user-message start cancels the pending reload, narrowing reconciliation away from ordinary UI-started runs. The visible `Goal complete` custom-message body alone reuses Pi Web's existing compaction Markdown class, giving it the 1.5 line height and paragraph, heading, list, quote, table, and code spacing intended for long summary content; its generic custom-message card and controls remain unchanged. Other custom-message types keep their upstream initial expansion behavior and presentation.

The exact-version transform patches only runtime-loaded compiled artifacts. It runs after branding because both transforms touch Pi Web page bundles, then versions browser references from the final display-patched client bytes so stale browser code cannot remain cached; uninstall removes it before restoring branding. Hashed manifests and distinct `.pui-reasoning-original` sidecars support verification, npm reconciliation, migration from an older verified PUI revision, checked removal, and cross-runtime rollback. The injected client renders the update notification card and an always-visible Restart PUI control (reusing the card styling, positioned below the notification). Restart sends `PUT /api/app-update`; the bridge rejects the request with HTTP 409 while an update or restart is already in progress, marks the status as restarting, then spawns a detached restarter that stops the managed Pi Web processes and relaunches Pi Web through the managed service on macOS (`launchctl kickstart -k`) or Linux (`systemctl --user restart`). Windows keeps the Startup-folder VBS as its hidden logon registration, but update and restart workers launch the absolute `%APPDATA%\npm\pi-web.cmd` shim directly in a detached hidden `cmd.exe`; this makes runtime recovery independent of an unobservable WScript child. Unmanaged POSIX installs fall back to detached `pi-web --no-open`. The restarter writes progress to the update status file and only reports success after Pi Web answers HTTP again. The client shows the restart phases on the card: on success the page reloads (returning an active Restart control); on failure the card reports the error and the button is re-enabled. A completed restart is consumed once and removed before normal release discovery resumes; retained restart failures remain actionable after reload. Before any bridge action loads `updater.js`, the bridge verifies the manifest's exact four-file extension shape and every recorded SHA-256. Detached update and restart workers carry a mandatory identity-check marker and repeat the same adjacent-manifest verification before executing; missing, extra, or drifted installed files fail closed. The restarter runs from the installed `updater.js` and never goes through the update transaction's idle gate.

Autostart suppresses Pi Web's npm updater because PUI owns the complete pinned composition. The PUI card checks the latest stable GitHub release once per app launch. After explicit approval, a detached worker stages tagged snapshots in OS temporary storage, waits for managed work to become idle, applies the target, and rolls back to the previous manifest-defined composition on failure. An unreachable Pi Web activity endpoint permits recovery only when process inspection confirms no managed Pi Web process exists; otherwise the idle gate fails closed. Target and rollback script output is retained at the OS temporary path `pui-update-last.log`. When an older rollback script completes restoration but fails at its obsolete restart boundary, the current worker relaunches Pi Web and accepts recovery only after the prior certified identity and live bridge validate. Transaction status is temporary and survives only long enough for the app to report the result.

## Files PUI does not manage

- `~/.pi/agent/sessions/`: user session data
- `~/.pi/agent/models.json`: model and provider configuration
- `~/.pi/agent/auth/`: credentials
- Project `AGENTS.md`, `CLAUDE.md`, and `.pi/settings.json` files outside this repository
- Host-specific MCP configuration for other applications
